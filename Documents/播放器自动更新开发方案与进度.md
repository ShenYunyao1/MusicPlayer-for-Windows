# 播放器自动更新开发方案与进度

日期：2026-10-24。适用仓库：`ShenYunyao1/MusicPlayer-for-Windows`。状态：方案已记录，功能尚未开发。

## 1. 目标与现状

目标流程：检查新版 → 展示版本与发行说明 → 用户确认 → 下载并验证 → 保存数据并退出 → 替换程序 → 重启并确认启动成功。失败时保留诊断信息，能够恢复上一版程序。

播放器与服务器各自维护版本、仓库、签名密钥和发行流程。客户端直接读取自己的 GitHub Release，不依赖音乐服务器转发更新，也不向 GitHub 发送音乐 API Key。当前两端名称都是暂定名称，更新端点与产品标识集中配置，后续命名调整时一并核对。

已核对当前代码：

- `MusicPlayer2/UpdateHelper.cpp` 仍获取原作者 GitHub／Gitee 的 `version.info`；`MusicPlayer2.cpp` 确认更新后仅打开下载链接。
- 当前版本比较使用字符串比较，需要改为数字语义版本比较，例如正确处理 `0.9.0 < 0.10.0`。
- 独立发行版本为 `client-release.json` 中的 `0.1.0`；界面上游版本仍为 `2.78`，Windows 资源版本为 `2,7,8,0`。自动更新前需统一客户端发行身份，原作者版本保留为来源信息。
- Actions 已具备测试、x64 打包、x86 编译检查及标签 Release。现有三个资产是 `MusicPlayer2.zip`、`MusicPlayer2.zip.sha256`、`client-release-manifest.json`；清单尚未签名。
- 播放器同时支持便携目录和 AppData 配置，并有全局单实例锁；正常关闭操作可能仅最小化到托盘，不能直接作为安装更新的退出操作。

当前 v0.1.0 没有自动安装能力。首次具有更新器的版本建议暂定为 **0.2.0**，需手动下载完整包升级一次；此后的版本才支持一键更新。版本号在正式发布前确认，不修改已经公开的 v0.1.0 资产。

## 2. 首期范围与技术选择

首期支持 Windows 10／11 x64、用户可写的本地安装目录。保留现有 ZIP 分发方式；x86 本期继续编译检查，不提供自动更新包。只读目录和 Program Files 无写权限时提前提示，并提供手动下载入口。管理员提权安装、ARM64、网络共享目录及无人确认的后台安装另行规划。

| 方案 | 适配成本与边界 | 选择 |
| --- | --- | --- |
| MFC 界面 + 独立更新器 | 保留便携分发和现有配置，能够处理退出、替换与恢复 | 推荐 |
| 迁移 MSIX 等安装体系 | 需要重新设计安装、签名、路径和分发方式 | 后续评估 |
| 使用 BAT／PowerShell 更新 | 依赖终端与脚本环境，复杂恢复和错误处理难维护 | 不作为产品实现 |

建议独立更新器使用 Go 编译为自包含的 `MusicPlayerUpdater.exe`，利用标准库处理 Ed25519、SHA-256、ZIP 和事务记录；终端用户不需要安装 Go、Python、Git 或 PowerShell。播放器继续使用原生 MFC 界面与独立 WinHTTP 下载模块。

应用安装目录固定包含 `MusicPlayer2.exe` 和 `MusicPlayerUpdater.exe`，名称不带版本号。构建产物继续放 `build/`，分发放 `dist/`，测试放 `test-results/`；不把测试脚本打入发行包。

## 3. 用户界面与操作流程

1. 保留“关于 → 检查更新”，在现有 `DataSettingsDlg` 的更新设置区放置启动检查选项和当前版本。更新来源固定为当前独立仓库，移除该区域原作者 GitHub／Gitee 切换项，作者鸣谢与帮助链接保留。
2. 手动检查立即请求；启动后台检查最多每 24 小时一次，可关闭。缓存检查时间，支持 ETag，正确处理断网、超时和 GitHub 限流；手动操作显示具体错误，后台检查失败不弹阻塞框。
3. 有新版本时显示当前版本、目标版本、发行说明、下载大小，提供“下载更新”“稍后”“跳过此版本”。首次仅通知，不擅自退出或安装。
4. 下载界面显示已下载／总大小、百分比、速度，以及“校验”“准备安装”等阶段。下载时播放器仍可使用，应用更新前可取消；首期断网重试重新下载，不承诺断点续传。
5. 验证成功且预检通过后，用户点击“安装并重启”。提示播放会中断；保存设置、播放位置及歌单，走专用退出路径，确保进程真正退出。
6. 更新器完成替换并启动新程序，只有新版本完成基础初始化并确认版本、提交号与事务身份后才判定成功。下次打开更新界面可查看结果及日志。
7. 无写权限、文件被占用、校验失败等情况给出具体处理方式和官方手动下载入口。GitHub 不可达时保持当前版本，不切换到未验证镜像。

## 4. 版本身份与签名发行协议

`client-release.json` 是客户端发行版本的唯一维护入口，构建时生成 C++ 版本头与 Windows 资源版本，界面、ZIP、清单、标签使用一致的版本与提交号。Windows 四段数字版本的映射由生成脚本固定，首期正式通道仅接受 `X.Y.Z` 稳定版本，忽略 draft／prerelease，不自动降级。

`server_baseline` 继续表示测试所用服务器提交／版本／schema，不作为客户端更新版本，也不直接用来限制 API v2 服务连接。

扩展 `client-release-manifest.json` 为有协议版本的清单，至少包含：

- 清单协议版本、产品标识、`windows-x64` 平台、客户端版本、源码提交号、最低更新器协议版本和签名公钥标识。
- 固定资产名、精确下载大小、ZIP SHA-256，以及程序文件的相对路径、大小和 SHA-256 清单。
- 与该版本绑定的发行说明；GitHub 页面元数据只作发现与展示辅助，实际安装身份以已验证清单为准。

新增独立资产 `client-release-manifest.json.sig`，使用客户端专用 Ed25519 私钥对清单原始字节签名。公钥编入更新器，私钥仅放受信任发行作业可访问的 Actions Secret，例如 `CLIENT_UPDATE_SIGNING_KEY`，不与服务器共享、不提交仓库。

构建顺序：程序与文件清单 → ZIP → 包含 ZIP 哈希的外置清单 → 签名。避免把含 ZIP 自身哈希的清单又放入同一 ZIP，形成循环依赖。正式包增加更新器后同步更新打包白名单与架构检查。

标签发布的固定资产由三个变为四个；同步修改 `publish.ps1` 的精确资产核对、下载验收和测试。签名、测试或资产核对任一失败都不得公开 Release。PR／普通构建使用测试密钥验收，不读取正式私钥；密钥缺失的正式标签作业明确失败。

SHA-256 用于完整性校验，签名用于确认发布来源；两者都必须验证。Ed25519 签名不等于 Windows Authenticode，不保证消除 SmartScreen 提示。公钥轮换需先由旧信任链发布含新公钥的过渡版本；首期不支持从网络任意指定新公钥。

## 5. 下载、校验与进程接口

新增 `UpdateHttpClient`，使用严格证书校验的 WinHTTP。不能直接复用会携带 `X-API-Key` 的音乐请求客户端，也不能复用旧更新代码中忽略证书名称错误的网络选项。

- 通过官方 GitHub Releases API 发现正式版本，限定预期仓库；下载仅允许 HTTPS 和明确允许的 GitHub 发行资产主机，限制重定向次数，禁止协议降级。
- 不读取或转发音乐 Key、登录 Cookie、GitHub PAT；公共 Release 不要求终端用户登录 GitHub。
- 限制元数据／签名体积、下载大小、超时和 ZIP 展开大小；先验签清单，再按已验证字段下载、校验载荷。
- 验证器必须拒绝未知清单协议、错误平台、非法版本、最低更新器不满足、包哈希／文件哈希不符和未签名旧发行；给出手动升级路径。

更新器拟提供三个稳定命令接口，详细 JSON 字段在实施时与测试一起固定：

| 接口 | 职责 |
| --- | --- |
| `--inspect` | 验签并输出可展示的版本／大小／说明；不执行安装 |
| `--verify-package` | 检查签名、ZIP 与每个文件，返回预检结果 |
| `--apply` | 重新验证输入，等待指定父进程退出，执行事务并监测重启 |

通过工作文件与结构化结果传递状态，命令行不携带凭据。父进程用进程句柄和创建身份识别，不能仅凭可能复用的 PID。状态文件不能授权任意命令或写入目标；更新器独立核对安装位置、路径边界、包身份和事务状态。

## 6. 数据保护、安装事务与恢复

更新只覆盖已声明的程序文件，不清空整个目录。便携模式与 AppData 模式都必须保留现有配置、`remote-library.json` 中的 DPAPI Key、歌单、曲目、缓存、插件和用户自建文件。

特别规则：**原地更新绝不覆盖或补建 `global_cfg.ini`**。完整新装包仍可带默认文件；原地安装时须跳过，否则可能把 AppData 用户切换成便携模式。其他首次安装默认文件也需区分“新装默认”和“可更新程序资源”。

- 应用退出前检查目录写入／重命名权限、可用空间、文件锁和安装目录类型。首期拒绝网络路径、重解析安装路径等尚未验证的情形，避免中途才发现不能安装。
- ZIP 只接受声明的普通文件；拒绝绝对路径、`..`、ADS、设备名、大小写重名、链接、重解析路径逃逸、过多文件和解压炸弹，检查已有目标路径也没有链接逃逸。
- 首期不自动删除旧版多余文件；后续删除需可信的旧文件归属清单。对可编辑皮肤／语言等资源，记录已安装基线，发现本地改动时报告冲突，不静默覆盖；基线不明时保守阻止受影响文件的自动覆盖。
- 将当前可信更新器复制到安装目录之外的私有事务目录后运行，便于更新安装目录内的更新器自身。待替换文件在目标卷暂存，以文件为单位保存旧程序并记录操作日志。
- 多文件替换不是一次原子操作。使用持久事务日志和可重复恢复步骤，记录“已验证 → 已备份 → 逐文件替换 → 待启动确认 → 完成／回滚”，覆盖强制终止和断电留下的中间状态。
- 新程序用事务随机标识与更新器握手；确认新版本／提交、主窗口与基础数据加载完成后才提交事务。仅进程创建成功不足以判定升级成功。
- 首期要求配置格式保持向后兼容，启动确认前禁止不可逆数据迁移；回滚只恢复程序文件，不回写用户操作产生的数据。
- 启动失败、超时或确认身份不符时恢复旧程序并尝试重启；回滚失败则保留备份和明确恢复指引。单实例锁被其他安装占用时明确报错，不关闭用户的其他播放器。
- 提供独立更新器的“恢复上次更新”入口。启动器／播放器检查未完成事务；若主 EXE 恰好缺失，用户仍能直接运行更新器恢复，不能声称断电后总能自动重启。
- 成功后保留最近一次恢复信息并受限清理事务空间；日志不记录 API Key、凭据或配置内容，界面提供打开日志目录的入口。

## 8. 分阶段执行与验收

当前仅完成调查与方案记录。后续获准开发后按依赖实施，每阶段验证通过再勾选并本地提交，未经当次明确要求不推送、不发布。

- [x] 阶段 0：核对现有更新代码、数据目录和 Actions 发布链，记录方案及范围。
- [ ] 阶段 1：统一客户端版本，确定清单／签名协议与密钥管理；实现独立验证器并更新打包、发布脚本的四资产门禁。
  - 验收：数字版本、错版本／提交、错平台、错签名、未知协议及包污染测试通过；普通构建无法触达正式密钥。
- [ ] 阶段 2：实现新版发现、手动／启动检查、发行说明、下载进度、取消与验签；此阶段不替换程序。
  - 验收：本地 HTTPS fixture 的成功、限流、超时、断网、重定向和篡改用例通过；不发送音乐凭据，失败不退出播放器。
- [ ] 阶段 3：实现专用退出、文件事务、重启确认与恢复入口。
  - 验收：在隔离目录覆盖正常升级、文件占用、空间／权限不足、任一步强制终止、启动失败与回滚；便携／AppData 配置与 Key 保持可用。
- [ ] 阶段 4：接入 Actions 全套门禁与桌面验收。
  - 验收：Windows 事务测试、x64 构建打包、x86 编译、Ubuntu 资产复核与现有协议测试通过；桌面检查托盘退出、播放中升级、中文／空格路径和单实例冲突。
- [ ] 阶段 5：确认版本与发行说明，按明确授权发布首个更新器版本，再验证后续真实签名升级。
  - 验收：首次手动安装后，使用第二个具有更新器的新签名版本完成端到端升级，并验证失败回滚；核对四资产、签名、源码提交和应用实际版本。

核心测试命令预计为 `go test ./...`（`updater/` 内）、Python 更新／打包／发布回归，以及既有 Windows 构建和客户端集成命令。具体参数随测试入口落地记录；本方案不声称这些新增测试已存在或运行。

完整非交互回归交 Actions，本地按阶段做针对性验证。托管 Actions 不代表桌面／音频播放已验收；真实更新测试使用隔离安装和测试数据，不连接生产音乐服务器。实施阶段需要生成客户端专用签名密钥并配置 Secret，无需把私钥或密码发送到聊天。
